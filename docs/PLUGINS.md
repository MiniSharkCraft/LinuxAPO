# Plugin support status

SkyAPO has native LV2, CLAP and initial VST3 audio-effect hosts. `skyapo plugin list` and `skyapo plugin scan` list built hosts; scanning and initialization are performed on the control/configuration thread, not in the audio callback. LV2, CLAP and VST3 support temporary live parameters and a format-neutral host bypass through `skyapo plugin bypass <PLUGIN-ID> on|off`; the opt-in FST/VST2 path also has live parameter and host bypass controls, but no discovery.

LV2 is discovered through Lilv's normal LV2 paths. Config syntax is:

```text
Plugin: LV2 https://example.org/plugins/my-stereo-effect
```

Input control ports may be overridden by symbol in the same directive:

```text
Plugin: LV2 https://example.org/plugins/my-stereo-effect gain=0.75 mix=0.4
```

Use `skyapo plugin info <URI>` to inspect input-port symbols, defaults and declared ranges before configuring overrides. SkyAPO rejects unknown symbols, duplicate assignments, non-finite values and out-of-range values during graph construction, so a failed hot reload leaves the prior graph active. Overrides are initialization values; automation curves and UI integration are not implemented.

The current host supports audio-only effects with the same number of audio input/output ports as the current selected channel set, plus input control ports initialized to LV2 defaults or config overrides. It rejects missing plugins, unsupported required LV2 host features, event/CV/other non-audio ports, and mismatched channel layouts. It accepts one latency output ControlPort using either deprecated `lv2:portProperty lv2:reportsLatency` or modern `lv2:designation lv2:latency`; the host queries it with `run(0)`, reads it after each processed block, and publishes only validated integer frame counts through lock-free atomics. The PipeWire control loop refreshes the published snapshot and host-bypass delay ring off the realtime thread. Invalid latency output is latched as a plugin failure. Plugin-reported latency participates in graph compensation, including `Copy` fan-ins and final output-channel alignment; fixed EAPO `Delay:` latency is also included, and oversized values are rejected before upstream delay buffers are initialized. This does not estimate total/end-to-end latency. When a block reports a changed effective latency, the callback requests a control-loop refresh and quiesces subsequent audio blocks until the new bypass/PDC schedules are ready, avoiding output with mismatched channel timing at the cost of a brief silent transition. Writable controls support `skyapo plugin set <URI> <symbol-or-name> <value>` on the uniquely matching active instance. Updates publish lock-free atomic values from the control thread; the audio thread copies them into stable LV2 control-port storage at the beginning of the next block. For plugins implementing `state:interface`, SkyAPO saves/restores Lilv LV2 state per config directive (canonical config path, line and plugin URI) under `$XDG_STATE_HOME/skyapo/lv2-state` or `~/.local/state/skyapo/lv2-state`. Save is exposed through the existing graph-quiesced state lifecycle; files are bounded, private and replaced atomically. Host URID mapping is preallocated/stable for lookup: previously unmapped URIs requested from a plugin's `run()` callback fail closed with URID 0, avoiding callback allocation or blocking. State data marked non-POD/non-portable and plugins requiring unsupported host features remain unsupported; no plugin UI or process isolation is provided. `tests/plugins/skyapo-test.lv2` is an ABI-compatible stateful fixture; CTest verifies default, overridden and live-updated gain numerically and saves/restores a changed gain across instances. The realtime allocator audit changes the live value before 1000 variable blocks. The private PipeWire E2E test also changes the LV2 gain through CLI/daemon IPC, then an independent client records the processed virtual source and checks its amplitude. This proves the fixture plugin's chain path, not third-party crash or allocator behavior.

CLAP uses the official header/API source pinned as the `upstream/clap` Git submodule (MIT; see its `LICENSE`). Set `CLAP_PATH` to a colon-separated plugin search path when needed; SkyAPO also checks `~/.clap`, `/usr/lib/clap`, `/usr/local/lib/clap`, and `/usr/lib64/clap`, recursively for `.clap` modules. The config directive is:

```text
Plugin: CLAP org.vendor.plugin-id
```

For a parameter override, use a stable numeric CLAP parameter ID (or a unique parameter name):

```text
Plugin: CLAP org.vendor.plugin-id 42=0.75
```

The first CLAP host version supports a single main float32 audio input and output bus with identical channel counts matching the active SkyAPO graph. `skyapo plugin info <CLAP-ID>` reports parameter IDs, names, defaults and ranges. A parameter may be set at graph-build time by numeric ID (preferred) or unique name, e.g. `Plugin: CLAP org.vendor.plugin-id 42=0.75`. Values are validated against CLAP's declared range; unknown, ambiguous, read-only, duplicate or out-of-range assignments reject the graph and preserve the previous live graph. `skyapo plugin set <CLAP-ID> <param-id-or-name> <value>` changes a writable parameter on the uniquely matching active plugin instance. Updates are validated off the audio thread and published through lock-free atomics; the callback assembles events in a buffer allocated during plugin initialization. Live values are not written back into config. For plugins implementing `clap.state`, SkyAPO saves/restores per-directive state sidecars keyed by canonical config source, line, and plugin ID under `$XDG_STATE_HOME/skyapo/clap-state` (fallback `~/.local/state/skyapo/clap-state`). Save occurs on successful graph rebuild and orderly daemon shutdown; pending parameter events are flushed before save. Corrupt state or plugin `load()` rejection fails candidate graph construction transactionally. Save briefly outputs silence while callbacks drain; see `docs/CLAP_STATE.md` for the synchronization, file bounds, and known limitations. Fixed config overrides are also sent as preallocated parameter events in each process block; plugin output-event handling is not implemented. It implements CLAP's thread-check host extension and serializes plugin processing/lifecycle calls. Fixture-backed dynamic latency notifications and graph delay compensation are supported as described in “Latency reporting status” below; this does not establish compatibility for arbitrary CLAP plugins. Native GUI, plugin crash isolation, and output-event handling are not implemented. Host bypass skips the CLAP process hook; for a nonzero initial latency snapshot, its dry path uses the preallocated delay described below. Bypass is temporary and does not change the plugin's own bypass parameter. A CLAP processing error is atomically latched: the current and subsequent blocks from that node are silent, and its process function is not called again. The `CLAP_PROCESS_ERROR` fixture test verifies that `Engine`/status diagnostics identify the plugin and config source line; a private PipeWire graph was independently consumed for 141312 frames at RMS zero after the error. The test fixture `tests/plugins/test_gain_clap.c` verifies main/audio-thread reporting, metadata, config overrides, live updates, state payload round-trip and bad-state rejection; private PipeWire E2E verifies a live update numerically in the consumed source. It is discovered with `CLAP_PATH`, checked numerically in offline rendering, and runs variable blocks under the allocator audit. A production CLAP plugin has not yet been validated.

The official Steinberg VST3 SDK's `base`, `pluginterfaces`, and `public.sdk` repositories are pinned as Git submodules under `upstream/vst3` (MIT-licensed). SkyAPO builds the Linux module/hosting subset; `skyapo plugin list` / `plugin info` enumerate installed audio-effect class IDs and writable normalized parameters. Discovery uses the SDK's standard paths and accepts colon-separated `VST3_PATH` roots or bundle paths. For hermetic tests, `SKYAPO_VST3_PATHS_ONLY=1` disables SDK system-path scanning and uses only `VST3_PATH`. Initial processing supports one matching mono/stereo audio input and output bus through `Plugin: VST3 <class-UID>`. Config may override writable normalized parameters by decimal ID, e.g. `Plugin: VST3 <class-UID> 7=0.25`; IDs and values are checked against plugin metadata (VST3 values use normalized range `[0, 1]`). `skyapo plugin set <class-UID> <ParamID> <normalized-value>` publishes a temporary live change, submitted to the plugin on the next audio block through preallocated VST3 automation queues. No controller/UI call is made from the realtime thread; live values are not persisted. Event buses, multiple/sidechain buses, plugin state, complete end-to-end latency reporting, UI, and crash isolation are unsupported. Reported VST3 latency does participate in graph per-channel PDC as described below; this does not provide a total PipeWire end-to-end measurement. A VST3 process result other than `kResultOk` is atomically latched; the node's current and subsequent blocks are silent and its processor is not called again. The fixture test checks that Engine/status reports the class UID and config source line. `tests/data/vst3_gain.txt` and `tests/data/vst3_parameter.txt` show fixture configs. The bundled SkyAPO-authored half-gain fixture is tested numerically offline (−6.0206 dB default and −12.0412 dB with a 0.25 override), exposes metadata through the CLI, rejects invalid IDs/ranges, and runs 1000 variable blocks with live updates under the callback allocation audit. A private PipeWire consumer E2E also changes ParamID 7 through CLI/daemon control and measures the new processed output. It was also run in the live physical-mic graph using `tests/data/vst3_realtime_chain.txt` on Built-in Audio Analog Stereo (F32 planar, 48 kHz stereo FL/FR, quantum 1024); an independent client recorded 192000 raw/processed frames and measured correlation 1, ratio 0.250594 (−12.0206 dB), with zero instrumented SkyAPO callback allocations/deallocations and overruns. The installed LSP Filter Stereo VST3 was also tested live: with Bypass enabled the independent client measured unity/correlation 1; with Bypass disabled and Input gain normalized to 0.82, it measured ratio 1.21256 (+1.674 dB), correlation 0.984988 over 192000 frames. The existing probe uses a strict correlation threshold for pure-gain checks, so it reports this active frequency-altering response as below that gate; the measured output nevertheless differs from the bypassed path. `examples/vst3-lsp-bypass.txt` and `examples/vst3-lsp-realtime-gain.txt` contain the two configs. A yabridge-produced ATKExpander VST3 wrapper (class UID `F2AEE70D00DE4F4E4D6174426E336C33`, yabridge 5.1.1) was also processed through a private 48 kHz/1024 mono PipeWire graph: the native consumer captured 143360 frames at RMS 0.00077680, matching daemon output RMS 0.00077629 from input RMS 0.0707117 (measured chain ratio 0.0109782 with Preamp plus expander). Status showed 1/1 links, 0 overruns, and 0 audited SkyAPO callback allocations/deallocations. The consumer's default `−6 dB` assertion returned 1 because the expander intentionally attenuated further; its nonzero capture and measured RMS establish consumption, not a preprogrammed-gain pass. The wrapper logs `realtime: no`, so this short run proves that samples traversed the host/wrapper but does not certify real-time safety or third-party stability. Its mono bus is correctly rejected on a stereo graph. One first attempt using long private XDG/Wine paths reported `File name too long` and a stack overflow; shortening the isolated paths removed that environment-specific failure. SkyAPO does not embed Wine or modify yabridge. The opt-in FST legacy ABI host is described in the section below; it is not production support. CLAP/VST3 bundles execute in-process and are not sandboxed; a crashing or malicious plugin can crash/compromise skyapod. Scanning loads module code in-process as the format discovery APIs require. The interfaces in `src/plugin/IPluginInstance.h` are the format-neutral boundary for these hosts.

### VST3 state persistence update

The earlier VST3 paragraphs saying plugin state was unsupported are superseded for plugins implementing `IComponent::getState`/`setState` or `IEditController` state methods. SkyAPO uses the pinned SDK `MemoryStream` on the graph-quiesced control path and stores component/controller blobs in a per-directive sidecar under `$XDG_STATE_HOME/skyapo/vst3-state` (fallback `~/.local/state/skyapo/vst3-state`). Sidecars include the canonical config source, line and class UID, are size-bounded/checksummed, use private permissions and atomic replacement. Restored state takes precedence over directive initialization overrides; plugins returning `kNotImplemented` for all state APIs are left unchanged and do not produce a sidecar. `skyapo-core` verifies an actual fixture parameter round-trip (`0.83`) and verifies that corrupt state rejects a reload while the last-good Engine continues producing the same output. This is core Engine evidence, not yet a daemon stop/restart or third-party-plugin state claim.

Clarification: the preceding VST3 summary's older “live values are not persisted” statement refers to the temporary CLI parameter update not being written back into the config file. When the plugin implements VST3 state APIs, its state is saved through the lifecycle above. “Normalized config source” means an absolute, lexically normalized path; it is not resolved through filesystem symlinks.

### Latency reporting status

Fixture-backed CLAP dynamic latency notifications and graph PDC are implemented and tested; this does not establish compatibility for arbitrary CLAP plugins. Current builds expose the sum of plugin-reported latency snapshots in `skyapo status` and `skyapo diagnostics --json` (`plugin_reported_latency_sum_samples`, plus a derived millisecond value when the sample rate is known). VST3 reads `IAudioProcessor::getLatencySamples()` after activation; CLAP reads the optional `clap.latency` extension, treating its absence as zero; LV2 supports both the deprecated port property and modern latency designation, polling its output after processing. The PipeWire control loop applies LV2 snapshots without concurrent access to the plugin-owned output port. The engine uses these values for per-channel path alignment, `Copy` fan-ins and final outputs. Fixed latency from the actual upstream EAPO `Delay:` filter also contributes to this alignment; core impulse tests cover a delayed `Copy` branch and the unmodified upstream `selective_delay.txt` fixture. Status's plugin-latency sum is not graph-wide or end-to-end latency. A reported dynamic change signals the PipeWire loop and quiesces subsequent callbacks until the refreshed graph schedule is ready; fixture E2E verifies the resulting stereo stream remains aligned (the transition can briefly be silent). Plugin-reported latency remains capped at 10,000 samples; Delay and compensation-ring storage share one 16 MiB per-graph budget. Zero-sample Delay uses a realtime allocation-free identity adapter to avoid upstream zero-length-buffer behavior. Delay sizes are checked before initializing each upstream Delay buffer, and PDC schedules are budget-checked before applying each alignment stage; an active refresh that cannot rebuild safely fails closed rather than resuming with stale alignment.

Each plugin-reported latency snapshot is capped at 10,000 samples (about 104–227 ms at 96–44.1 kHz); total PDC ring memory is capped at 16 MiB, without an additional per-ring 10,000-sample cap. An oversized initial plugin snapshot rejects the candidate config and preserves the active graph. If an active plugin later reports an oversized individual latency, SkyAPO latches that instance as failed/silent and rebuilds the graph schedule using zero latency for that plugin; an aggregate-budget failure during refresh fails closed and stops the runtime rather than processing with stale alignment. These are safety bounds, not latency targets or end-to-end guarantees.

For a Windows plugin, install/configure yabridge yourself, then run its normal sync workflow (for example `yabridgectl add <plugin-path>` followed by `yabridgectl sync`). SkyAPO only scans the generated Linux VST3 bundle; it does not call yabridgectl or manage Wine. Find its class UID using `skyapo plugin list`, then use `Plugin: VST3 <class-UID>` in the config. Check the channel count first: the initial host rejects layouts that do not exactly match the active mono/stereo graph.

### VST2 ABI host status and release gate

SkyAPO now has an opt-in FST-backed VST2 ABI processing path, not merely a standalone feasibility test. Enable it with `-DSKYAPO_ENABLE_FST_VST2_HOST=ON`; the option links the host and `IFilterFactory` adapter into `skyapo-core`, so a config can use a native Linux module:

```text
Plugin: VST2 "/path/to/effect.so" 0=0.5
```

This loads the module in-process, accepts 32-bit float mono/stereo effects that expose `processReplacing`, applies numeric parameter-index overrides during graph construction, supports temporary host dry bypass, latches processing failures, and reports the plugin's initial `AEffect::initialDelay` snapshot. This is not plugin discovery: `skyapo plugin list/info` do not enumerate VST2 modules. Live parameter changes by numeric index or unique display name are available through the shared CLI control API; they are temporary and coalesced through preallocated lock-free latest-value mailboxes, with `setParameter` consumed at a process-block boundary. Saved state/chunks, UI, automation/events, shell plugins, multiple buses, broader callbacks, crash isolation and arbitrary third-party compatibility are not implemented. A crashing or malicious module can still terminate or compromise `skyapod`. The default build and Arch package keep the option disabled. In the private PipeWire E2E, an independent consumer recorded 143360 frames after a live parameter update and measured RMS ratio `1.000044` against the expected output; SkyAPO reported zero callback allocations/deallocations and zero overruns. This is fixture evidence. A locally installed yabridge 5.1.1 Blue Cat Gain 3 VST2 wrapper also loaded and traversed offline rendering at 44.1 kHz stereo, but default and `0=0.0`/`0=1.0` overrides all measured unity output; yabridge reported `realtime: no`. This limited probe does not establish a parameter effect, independent PipeWire consumption, realtime safety, or general third-party compatibility. See `docs/VST2_PROTOTYPE.md` for the exact scope and test commands.

The adapter uses the pinned, independently reverse-engineered [FST](https://git.iem.at/zmoelnig/FST) API (`upstream/fst`), not Steinberg or EAPO `aeffect.h` / `aeffectx.h`. FST is GPL-3.0-or-later, incomplete, and its README warns about the `VST` trademark and compatibility naming. Steinberg's [current licensing FAQ](https://steinbergmedia.github.io/vst3_dev_portal/pages/FAQ/Licensing.html) says source sharing is allowed without redistributing Steinberg's VST2 headers, while distributing a VST2 host binary requires a VST2 agreement signed before October 2018. That FAQ does not itself determine the legal status of SkyAPO's independently implemented FST path. FST's license, trademark warning, the combined SkyAPO/EAPO licensing obligations, packaging and public product claims still require qualified review; do not treat this implementation or the absence of Steinberg headers as clearance. The GPL/LMMS-derived EAPO header `upstream/equalizerapo/helpers/aeffectx.h` is not a Steinberg license and is not used by this host.

VST2 remains a 1.0 product requirement and its acceptance is intentionally open. The release gates are: review/resolve the legal and trademark questions for source and binary distribution; keep package exposure disabled until approved; validate the FST ABI against permitted third-party native modules and yabridge-generated Linux wrappers; add third-party offline and independent-consumer PipeWire evidence; and decide which remaining host features (notably state/chunks and crash isolation) are required for the promised compatibility level. Yabridge does not remove the need for a VST2 host: its Linux VST2 wrapper still has to be loaded by a host that understands that interface. Do not claim broad third-party compatibility from the SkyAPO-authored fixture alone.

### Live plugin parameter control

For an LV2, CLAP, VST3, or opt-in FST/VST2 instance already present in the active configuration, the CLI can update a writable parameter without rebuilding the graph:

```sh
skyapo plugin set https://example.org/plugins/noise-gate threshold 0.75
skyapo plugin set org.vendor.plugin-id 42 0.75
skyapo plugin set 534B5941504F00010000000000000001 7 0.4
skyapo plugin set /path/to/effect.so 0 0.75
```

The daemon requires exactly one matching active plugin ID and validates the parameter/range on the serialized control loop. LV2 writes the new value into its existing control-port storage at a block boundary; CLAP and VST3 publish lock-free atomic mailboxes which the callback turns into preallocated process events/queues; VST2 publishes an indexed/name-matched latest-value mailbox, and the audio thread calls `setParameter` at a process-block boundary. The update takes effect on a subsequent process block. It is not persisted to config; CLAP plugins implementing `clap.state` are persisted to a state sidecar at graph rebuild/orderly daemon shutdown, and LV2 plugins implementing `state:interface` use Lilv state files as described above. VST3/VST2 plugin state persistence remains unsupported. CTest covers numerical, invalid-value, state-restore and callback-allocation cases for the supported hosts, plus private PipeWire tests where independent clients consume LV2/CLAP/VST3 outputs and the VST2 fixture's live parameter change. Automation curves and plugin GUI remain unsupported.

Host-level bypass is available for active LV2, CLAP, VST3, and opt-in FST/VST2 fixture/instances with the common identity interface:

```sh
skyapo plugin bypass org.vendor.plugin-id on
skyapo plugin bypass org.vendor.plugin-id off
```

When enabled, the wrapper skips the plugin process function. If the host reports latency, the dry path delays input by that many samples using a ring buffer allocated/rebuilt on the control thread; zero-latency hosts retain direct dry copying. CLAP/VST3 notifications and LV2's polled output refresh this host-bypass snapshot while the graph is quiesced. Reported plugin latency also participates in graph PDC for supported paths. Because the plugin is not processed while bypassed, its internal state freezes and may produce a transition artifact when bypass is turned off; there is no crossfade. Bypass does not change the plugin's own bypass parameter or save plugin state.

### LV2 dynamic latency output

An LV2 latency port is sampled on the audio thread only after `lilv_instance_run()` returns, then an integer snapshot is published through a lock-free atomic. The callback signals the PipeWire event loop and quiesces subsequent blocks; the control loop never reads the plugin's non-atomic output-port storage concurrently, consumes the snapshot after callbacks drain, and rebuilds host-bypass/PDC schedules off-thread before resuming. `run(0)` seeds the initial snapshot. Core fixtures cover both LV2 declarations, a live change from 64 to 32 frames, impulse offsets, host bypass and 1000 variable blocks with zero callback allocations; a private PipeWire E2E independently records across the latency transition and verifies equal stereo channels, lag 0 and expected RMS. Plugins that change latency while already bypassed are not run, so their latest value cannot be observed until processing resumes.

### VST3 dynamic latency notification

VST3 `IComponentHandler::restartComponent(kLatencyChanged)` is now handled through an atomic notification mailbox. The audio callback only reports the pending flag; the PipeWire control loop quiesces/drains callbacks, deactivates and reactivates the component, reads the new latency, rebuilds host-bypass/PDC schedules, then resumes processing. The fixture and private PipeWire E2E verify a live change from 32 to 64 samples and an independent consumer sees the stream; the callback allocation/deallocation counters remain zero. The lifecycle transition briefly interrupts processing, as required for the VST3 restart sequence. Other restart flags fail closed, and auxiliary buses, crash isolation, and third-party dynamic-latency coverage remain unsupported.

### CLAP dynamic latency notification

SkyAPO exposes `clap.host.latency` and atomically records `changed()` and `request_restart()` notifications. The PipeWire control loop drains callbacks, stops/deactivates/reactivates the CLAP instance, validates that its single main audio-bus layout remains supported, rereads `clap.latency`, rebuilds host-bypass/PDC schedules and resumes processing. The CLAP fixture changes from 32 to 64 samples; core impulse/bypass tests and a private PipeWire E2E with an independent consumer pass (144384 frames, expected-output RMS ratio `1.000007`, zero audited callback allocations/deallocations and zero overruns). A restart that changes the supported bus layout fails closed rather than using stale channel metadata. The lifecycle transition briefly interrupts processing. Other format/bus coverage and third-party compatibility remain incomplete. This section also supersedes the earlier CLAP paragraph's statement that dynamic latency changes were not implemented and the general bypass paragraph's statement that later latency changes are not tracked.

The Lilv catalog is initialized lazily on first LV2 scan/use and retained once for process lifetime, so ordinary EAPO-only configs do not scan plugin bundles and hot reloads do not rescan them. On the current Arch Lilv 0.28.0 build, LeakSanitizer finds a 24-byte allocation left unreachable by `lilv_world_load_plugin_classes`; sanitizer CTest narrowly suppresses that external stack only. The plugin-list command separately frees all returned plugin-name nodes.
