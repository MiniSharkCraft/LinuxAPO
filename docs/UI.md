# UI port audit and status

The first SkyAPO GUI target, `skyapo-ui`, builds with Qt 6 Widgets. The pinned upstream `Editor/Editor.pro` is a Qt Widgets application (`core`, `gui`, `widgets`) built from a real configuration editor, filter-row/factory system, specialized filter widgets, custom Qt graphics widgets, and response-analysis views/worker. The current target directly compiles selected upstream GUI source files from the submodule; it does not copy/rewrite those controls.

## Reuse candidates

- `Editor/FilterTable*`, `FilterTemplate*`, `IFilterGUI*` and `IFilterGUIFactory*` implement the ordered configuration/filter-row model and plugin-like per-directive editor registration.
- The Preamp, BiQuad, Delay, Channel, Copy, Include, GraphicEQ and Convolution GUI classes provide concrete controls and serialize EAPO directives. They should be ported with their upstream notices intact, then enabled only for directives SkyAPO actually validates.
- `Editor/widgets/FrequencyPlot*`, `GraphicEQFilterGUI*`, `AnalysisPlot*` and `AnalysisThread*` contain reusable Qt scene/view and response-analysis behavior. Their actual input/calculation contract must be reconciled with SkyAPO's active graph before presenting a response as authoritative.
- `Editor/FilterTableRow.ui`, `MainWindow.ui`, per-filter `.ui` resources, translations and Qt resources preserve the original interaction/layout vocabulary.

## Windows integration that must be replaced

`MainWindow.cpp` discovers input/output `DeviceAPOInfo`, checks APO registration and Windows enhancement state, offers repair/install prompts, and contains `ShellExecuteW(..., "runas")` elevation, `CreateFile`/Win32 error handling, and registry-backed configuration/settings paths. `main.cpp` obtains the config directory and language from the Registry and writes editor state through `QSettings::NativeFormat`. Device filter GUIs operate on `AbstractAPOInfo`/`DeviceAPOInfo` and Windows channel masks. The VST GUI selects Windows `.dll` files and performs Local Service ACL changes. These are not portable UI details: the Linux window must query/control `skyapod` (stable PipeWire device identity, negotiated format and virtual source), use XDG paths, and delegate all plugin behavior to the daemon/host.

## Current implementation

Runtime status distinguishes PipeWire's filter state from the DSP engine state:
the editor reports active processing only when the negotiated DSP graph is
running, and labels initialization, format reconfiguration, quiescing/output
silence, and faulted/output silence explicitly. This avoids presenting a newly
connected PipeWire filter or a fail-closed DSP graph as healthy audio processing.

Recent-file/preferences support is now implemented: **File → Open Recent** retains up to ten absolute config paths, missing paths are omitted, the last-open directory is remembered, and window geometry/state is restored through `QSettings`. The older summary paragraph below predates this addition; recent-file/preferences tests run as part of `skyapo-ui-editor`.

The Linux shell includes an XDG-default config path, Open/Save, Save & Check, Save & Reload, daemon status/start/stop, input device enumeration/selection, an add-filter menu, row removal, and inline text editing for directives without an implemented visual editor. The device selector shows enumerated channel count and sample-rate metadata when available; unavailable rate metadata is not inferred. It reuses the actual upstream `FilterTableRow` widget, icons, compact toolbar and escapable text field through a small Linux adapter. The adapter provides ordered focus/selection, Ctrl-click toggle, Shift-click range selection, Delete removal, Escape to clear selection, and Alt+Up/Alt+Down to move the focused row. Reordering preserves unchanged row text and the document's newline style; drag-and-drop and the Windows-bound full `FilterTable` factory/device integration are not ported. `Preamp:`, parametric `Filter:`, `Delay:` and `Stage:` rows instantiate their actual upstream GUI widgets/factories. `DeviceFilterEditor` provides a basic `Device:` match-pattern field and Add Filter template; it edits the selected-source predicate, not device enumeration/selection or the upstream endpoint-state dialog. Qt integration tests verify config-row creation and edit/save serialization. The upstream `Editor` source has no GUI for the custom-coefficient `IIR` filter type; SkyAPO supplies its own visual `IIRFilterEditor` for explicit numeric coefficients (orders 1–256), preserving the EAPO `b0…bm a0…am` order. Inline expressions, malformed values, and orders outside that UI range remain raw text rather than being guessed or normalized. `Channel:` and `Copy:` use narrowly scoped Linux Qt editors that serialize the actual EAPO syntax: Channel supports `ALL`, L/R/C/LFE/RL/RR/SL/SR (and the upstream `SUB` alias); Copy supports one or more named-channel assignments with a single finite linear factor per source. Unknown/numeric Channel labels, sums, dB factors and constant Copy sources intentionally stay raw text because the upstream widgets depend on Windows channel/device context and the Linux editors do not claim those semantics. `GraphicEQ:` also uses the upstream `GraphicEQFilterGUIFactory`, table/plot editor, graphics scene and frequency-plot widgets when FFTW3f and the corresponding core feature are enabled. The upstream band presets and variable-band mode are available in the add-filter menu; editing a table band updates the plot/model, and Save serializes the edited frequency/gain pairs back to the directive. If FFTW3f is unavailable, the GraphicEQ-specific GUI sources/factory are not built or dispatched: the directive stays visible as raw text, is not represented as a valid visual editor, and core validation reports the missing FFTW3f support. `Include:` has a Linux editor with relative-to-config path resolution, existence feedback, and a native file picker; nested diagnostics retain the parser's actual Include ancestry, mark the corresponding root `Include:` row, and offer `Open error location` to open/select the failing included source line. It intentionally omits upstream's Windows service-ACL check and tab-navigation action. `Convolution:` now has a Linux adapter row (the upstream GUI depends on Windows Registry/access-control and wide-file APIs): it preserves the EAPO directive/path, resolves relative paths against the config file, offers file browsing, and leaves IR format/rate validation to the authoritative config checker. Qt tests cover path-with-spaces round trips, template insertion, Save behavior, missing-file diagnostics, nested Include source navigation, and checker acceptance/rejection of a real WAV impulse response. Existing automated tests also cover control loading/serialization for each visual widget, Channel/Copy and IIR boundaries, row selection/reorder/save, GraphicEQ edits and the upstream row widget. `ConfigFile` retains untouched line bytes and line endings so comments, includes, whitespace and unsupported-but-preserved rows are not reformatted unless edited. Save uses `QSaveFile`; closing with unsaved changes prompts.

The process is a daemon client and invokes the existing `skyapo` CLI for status, start/stop, device selection, config validation and reload. This keeps the audio graph in `skyapod`; control calls are outside realtime. CLI requests run asynchronously through `QProcess`; status refreshes every two seconds and device inventory every five seconds, while overlapping requests are coalesced so a slow PipeWire query does not block the UI or create an unbounded child-process backlog. Device list's selected marker supplies current selection, avoiding a second serialized CLI query. If a selected stable node disappears, the selector shows an unavailable placeholder carrying its prior `node.name` instead of falsely selecting the first remaining device; the daemon's persisted selection is unchanged until the user explicitly picks another input. A Qt integration test launches delayed/changing CLI fixtures and verifies event-loop responsiveness, disappearance/reappearance handling, and retention of stable identity.

The **Device Selector…** dialog presents separate capture and playback endpoint tables from `skyapo device list` and `skyapo device output list`, including selected state, description, node name, available channel/rate metadata, and default status. Its selection buttons use stable-name CLI commands; playback selection changes only LinuxAPO's own graph and does not change the desktop default or move unrelated application streams. When `skyapod` is active, selecting a compatible playback sink retargets the existing PipeWire smart-filter graph in place, preserving the virtual mic and application-to-filter links; capture selection still restarts the daemon and briefly interrupts both graphs. A stopped daemon only saves either preference for its next start. Device inventory is refreshed every five seconds while the dialog is open (overlapping refresh requests are coalesced), and the Refresh button remains available. If the last daemon-confirmed selection disappears, the table retains it as unavailable and disables the Apply button until it returns or another available endpoint is selected. The collapsed **Troubleshooting and graph details** disclosure reveals live daemon/playback status only when requested. **Verify audio path…** runs asynchronous, read-only config, daemon, capture-link, virtual-microphone, and playback-link checks. It never starts/restarts the daemon, changes routes, or emits a test signal. Numerical DSP correctness and physical microphones/speakers remain explicitly **NOT TESTED**. The Qt fixture test covers healthy, stopped, initializing, disconnected, unknown, faulted, and command-failure results; command failures include their exit status and diagnostic, and the fixture verifies that verification sends only read-only CLI commands. The private PipeWire/WirePlumber output-switch E2E invokes the actual selector verification against live graph nodes, switches sinks while an ordinary app stream is active, and independently records processed output from the new sink. Numerical DSP and physical hardware remain untested by the dialog. These tests do not prove arbitrary desktops, layouts with a different channel count, or physical-device switching behave identically. Incompatible playback channel layouts return an explicit restart-required error. This remains a partial Windows Device Selector equivalent: there is no per-device enable/install state, user-visible route rollback UI, or broad physical hardware validation. Per-user PipeWire endpoint selection does not justify broad root privilege.

For the verification dialog, the **Configuration** row passes only when `skyapo config check` validates the saved editor file and its canonical path matches the `Config:` path reported by the running daemon. If the editor has unsaved edits, the dialog explicitly says those edits are excluded; save and reload them before treating them as active. A valid but different editor file is not misreported as the daemon's active configuration. A failed status/device query or missing/unparseable graph fields produce `UNKNOWN` for the affected check, with the command's exit status and diagnostic included when available. `FAIL` is reserved for a successfully observed state that contradicts the required condition (for example, a stopped engine or missing route links); `UNKNOWN` never counts as verification success.

Opening the Device Selector runs an asynchronous PolicyKit authorization preflight (`org.linuxapo.device-selector.open`) in the normal user process. Denial/cancellation or a missing `pkcheck` keeps the selector closed and reports why. This is only an opening gate: the editor and selector never run as root, no privileged helper is provided, and endpoint selection remains per-user PipeWire configuration. The policy action does not authorize arbitrary system operations.

Live validation now marks the matching root-config filter row with a red line number, hover text and accessible description; nested-file errors use parser-owned Include ancestry to mark the root Include row and the **Open error location** action opens/selects the actual source line. Markers clear immediately when the document changes and are reapplied only by the latest validation revision, preventing stale errors from sticking to rows.

When built with FFTW3f, `Analyze response` can analyze the saved default `config.txt` or the current editor document, including unsaved edits. It writes the selected source to a same-directory temporary snapshot and runs analysis on a worker thread. A fresh actual `Engine` processes an impulse independently for each input channel at the selected format, then FFTs each output channel, so channel-copy/routing paths are represented rather than assumed away. The plot shows both magnitude (dB) and wrapped phase (±180°) for every input/output channel path; its upper frequency limit follows the analyzed Nyquist frequency up to 24 kHz. Phase is shown as undefined where the magnitude is at or below the −240 dB analysis floor. The user can select persisted power-of-two FFT sizes from 128 to 1,048,576 samples (default 16,384); the upper bound is narrower than upstream EAPO's 8,388,608. Estimated sample, FFT and curve buffers are limited to 64 MiB; additional `Engine` and FFT-library allocations are not included in that estimate. A large FFT combined with many channels may therefore be refused before buffer allocation. The plot is a calculated theoretical response from the Engine impulse output, not a measurement of the active PipeWire graph. Plugin filter factories are deliberately disabled for this analysis so third-party module code is never loaded into the editor process; configs containing plugin directives therefore return a clear analysis error. The finite impulse window truncates longer tails, and nonlinear or time-varying plugin behavior cannot be treated as a universal linear frequency response; this view is a diagnostic, not a substitute for runtime measurement. Analysis is disabled when FFTW3f is unavailable. Qt integration coverage verifies source selection (−6 dB from saved default and −3 dB from unsaved current file), 128-sample partial-block output, maximum 1,048,576-sample mono analysis, an over-budget eight-channel request, 8,192-sample resolution producing 4,096 bins, combined `Preamp: -6 dB` plus 1 kHz +6 dB parametric response near −6 dB at 100 Hz and 0 dB near 1 kHz, a delayed impulse's expected phase near 1 kHz, and undefined phase below the analysis floor.

The Add Filter menu now follows the Windows reference category order: Comment, Control, Basic filters, Parametric filters, Graphic equalizers, Advanced filters, and Plugins. Graphic EQ choices remain visible but disabled with an FFTW3f explanation in builds without FFTW3f. Plugins keeps separately named `VST plugin (Linux)` and `VST plugin (Windows)` entries: the Linux picker filters to modules accepted by the Linux VST3 host, while the Windows entry explains that Windows binaries are not loaded directly and no dedicated Wine/yabridge integration is provided. A yabridge-produced Linux VST3 wrapper might be discoverable through the Linux VST entry, but that path has not been verified here. LV2/CLAP/VST3 remain available under the explicitly format-labeled installed-plugin picker. The upstream Loudness correction engine filter has a menu entry, with a warning that it requires a live PipeWire endpoint-volume snapshot.

The upstream Stage widget is reused. `Stage: capture` and `Stage: post-mix` can be selected in the Linux editor; `pre-mix` remains visibly disabled with a tooltip because the PipeWire graph has no per-application pre-mix stage. The backend maps the capture Engine to `stage == "capture"` and the PipeWire playback Engine to `stage == "post-mix"`; `If:` and `Stage:` post-mix sections therefore apply to playback. A private PipeWire/WirePlumber E2E measured playback at −6 dB (RMS ratio 0.999997 to expected) while capture remained unity (1.000041). Unsupported `pre-mix` is reported with a file/line warning. Editor serialization of post-mix selection is covered by `skyapo-ui-editor`; physical playback validation remains a separate gate. The editor can insert discovered LV2/CLAP/VST3 directives and, via Tools → **Configure selected plugin parameters**, edit writable parameter values in the config row. Metadata is queried from the CLI; values shown are saved config values, not live plugin readbacks, and Save & Reload is required to apply edits. This does not provide a plugin state editor or native plugin GUI. There is also no syntax highlighting, translation integration, or comprehensive GUI automation. Recent-file navigation and basic window/config-directory preferences are implemented as described above. Unsupported lines remain editable as raw text and are not presented as valid. The device/status presentation is the CLI's actual response, not simulated state.

## Port boundary

CLI subprocesses are asynchronous, coalesced where periodic, and each has a
30-second deadline. A stalled CLI request is terminated and reported in the
window instead of leaving device/status/config controls pending forever;
`skyapo-ui-editor` covers this timeout with a delayed CLI fixture.

Keep the daemon as owner of PipeWire, DSP, config validation/reload and plugins. The GUI is an IPC client and closing it must not stop audio. Port the upstream filter-table/editor widgets and response visualizations incrementally where their config semantics match SkyAPO; replace the Windows `MainWindow` shell, device/APO setup, registry persistence and VST DLL UI with Linux/daemon-backed implementations. Preserve hand-written config/comments where practical, and never claim the displayed response matches runtime until it is computed from the active graph.

The development environment has Qt 6 Widgets 6.11.2. The upstream project remains an older qmake project with Windows-specific linker flags and hard-coded `C:/Program Files` paths for libsndfile, FFTW and muparserX. SkyAPO avoids those settings and currently builds a selected subset with CMake; the upstream checkout remains clean. The upstream Channel/Copy widgets were inspected but excluded because they depend on Windows channel masks/device configuration and the Windows-bound filter-table context. Building the upstream GraphicEQ plot widgets currently emits deprecation warnings for older `QMouseEvent` coordinate accessors; they have not been changed in upstream. Qt Core/Gui/Widgets are dynamically linked from the host distribution; the app Help → About dialog identifies Qt and its LGPL-3.0 use, and staged install/package tests require the LGPL license text. The curated resource paths expected by the selected upstream widgets now point to project-authored SVG icons rather than upstream art with unverified per-file provenance; the full `Editor.qrc` remains excluded because it also bundles unused translations and a calibration FLAC. The separate Qt/distribution license review remains part of release hardening. See [UI license audit](UI_LICENSE_AUDIT.md).
