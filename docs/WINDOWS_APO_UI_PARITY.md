# Equalizer APO 1.4.2 UI reference parity

This audit compares the 16 user-provided PNG references in `example-windows/`
with the LinuxAPO UI on public `main` at `afacf0c443537cba3dc132fb357769ca88ce4e6d`
and with the specifically identified open PRs. The image files were inspected
visually for this audit, but are not copied into the repository: they are local
reference material and no redistribution grant for them has been recorded.
Filenames below are inventory identifiers, not links to files shipped here.

The statuses describe user-visible behavior, not resemblance of widget names.
Open PRs are identified separately and do not count as shipped on `main`.

## Status definitions

- **IMPLEMENTED AND VERIFIED** — the pictured workflow is available on public
  `main`, with source/test evidence appropriate to the claim.
- **IMPLEMENTED BUT INCOMPLETE** — some pictured behavior exists, but material
  controls or semantics are missing or restricted.
- **UI ONLY** — controls are visible without the corresponding runtime effect.
- **NOT IMPLEMENTED** — no corresponding Linux UI/workflow exists.
- **BLOCKED** — implementation depends on an unresolved prerequisite or external
  decision.
- **NOT APPLICABLE ON LINUX** — the pictured operation is specific to Windows
  APO/COM/Registry installation and should not be copied literally.

## Findings that affect implementation order

1. The Linux editor already has useful capture selection and config editing,
   but that is not equivalent to the Windows multi-device Device Selector.
2. Windows installation/testing controls must be replaced by truthful graph
   diagnostics; their labels and “installed” state must not be copied literally.
3. The Add Filter menu, plugin insertion workflow and response analysis are
   active parity work. PR #10 and PR #15 contain candidate improvements, but
   remain unmerged and are not counted as public-main behavior here.
4. The Windows install tree is a visual reference only. Linux packaging should
   retain XDG, `GNUInstallDirs`, systemd-user and distro dependency conventions.
5. The analysis plot is theoretical. A separate PipeWire consumer and physical
   device run are required for claims about actual playback/capture behavior.
